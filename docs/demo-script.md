# SeaTrack 良率异常与 RCA 证据分诊演示脚本

- 建议时长：12 分钟
- 受众：无锡工厂业务负责人、产品/性能工程、质量/FA、GFIT/MES、信息安全
- 演示地址：`http://127.0.0.1:8787`

> 开场必须说明：所有数据和 `F127` 均为合成示例；演示验证交互与安全机制，不代表 Seagate 真实流程。

## 1. 开场：先讲业务问题（1 分钟）

建议话术：

> 我们今天不演示一个通用聊天机器人，而是演示一次异常发生后的首轮分诊。系统不会确认根因，也不会控制设备；它只把制造上下文、相似历史案例和当前有效文档组合成可验证的检查路径。

## 2. 单站异常（3 分钟）

选择“单站异常”场景。

让听众观察：

- 系统识别产品、站点、Failure Code、程序版本和单站范围；
- 排名前列的是设备/校准类案例，而不是仅按 `F127` 文本匹配；
- 每个案例显示相似条件、不相似条件和证据；
- 建议是“先检查什么”，不是“根因就是某设备”。

现场提问：

> 在你们真实流程中，单站异常最先看哪三个信号？这里缺了什么？

## 3. 相同 Failure Code，不同上下文（3 分钟）

依次运行：

1. “物料集中”；
2. “程序变更”。

强调：

- Failure Code 不变，但异常范围、批次和版本变化；
- 排序应该随制造上下文变化；
- 这正是结构化上下文 + RAG 比纯关键词搜索更重要的地方。

现场提问：

> 无锡现场哪些上下文字段最能区分设备、物料、程序和产品问题？

## 4. 无答案与安全边界（2 分钟）

运行“无答案”：

- 证据不足时系统升级，不编造历史案例。

运行“安全边界”：

- 要求跳过测试、改参数或放行时，系统拒绝；
- 说明生产版仍需结合身份、角色、文档权限和审计。

现场提问：

> 除了这些动作，还有哪些请求必须一票拒绝？

## 5. 反馈闭环（1 分钟）

展示调查记录和工程师反馈：

- 接受、部分有用、无用或有风险；
- 记录原因，而不仅是点赞；
- 经审核后把已关闭调查沉淀为新案例。

强调：系统必须允许工程师纠正它，否则不会形成可靠的工厂知识。

## 6. 收口到 PoC 决策（2 分钟）

建议话术：

> 下一步不是直接接入全工厂，而是用 50–100 个已关闭历史问题做盲测，再进行不影响现有流程的影子试运行。只有检索、引用、安全和时间节省同时达标，才建议进入生产化。

请现场确认四件事：

1. 首个 SeaTrack 异常族和站点是否已经选定；当前 SelfTest/F127 仅是合成演示标签；
2. 谁是业务负责人和工程 SME；
3. 哪些脱敏数据可以用于 6 周 PoC；
4. 谁在第 6 周做 Go / Adjust / Stop 决策。

## 7. 演示故障备用方案

如果本地服务无法打开：

1. 使用汇报 PPT 第 4–7 页讲述输入、检索、边界和输出；
2. 展示 `README.md` 中的 API 示例；
3. 不现场修改代码或连接外部模型；
4. 记录问题，承诺会后提供可重复运行日志。
