# SeaTrack 痛点解决方案与最终工程审计

日期：2026-07-30
结论：仓库已经形成一套可运行的制造问题解决方案——在 SeaTrack 类 MES 发现良率异常后，为工程师汇集上下文相关、版本有效且权限允许的 RCA 证据，支持首轮排查、质量复核和知识沉淀。它仍应明确标注为合成数据 PoC。

## 要解决的业务问题

异常监控只能告诉工程师“哪里变差了”，不能自动完成“为什么变差”的证据调查。历史案例、SOP、FA、维护、物料与程序变更分散在不同来源；相同 Failure Code 在不同站点、批次和版本上下文中可能对应不同根因。

本项目把目标限定为：缩短首轮证据获取路径、提高历史案例复用和引用可追溯性，同时把最终根因和所有生产动作留给授权人员。

## 已形成的解决方案闭环

1. 接收异常事件和产品、站点、Failure Code、批次、版本上下文；
2. 在权限与文档版本过滤后检索历史案例和工程资料；
3. 返回事实、相似案例、差异、检查步骤、引用与升级条件；
4. 工程师记录实际检查结果，质量角色审核，人工发布最终调查；
5. 受治理的新案例进入来源账本，成为下一次异常的可复用知识；
6. 无证据和高风险控制请求分别进入升级和拒绝路径。

## 本轮完成

- HTTP 服务不再在模块导入时创建全局业务服务和数据库副作用，运行实例显式拥有 `TriageService`；
- 所有响应加入安全的 `X-Request-ID`，错误体包含稳定 `error_code`、状态和关联 ID，访问日志使用结构化 JSON 且不记录原始查询串；
- 服务版本提升到 `0.6.0`，健康检查暴露版本、认证边界与生成模式；
- 新增 Responses API 兼容的可选模型网关，只接收权限过滤后的证据并使用严格 JSON Schema；
- 模型候选假设在服务端二次校验结构和证据 ID，拒答、高风险、弱证据、超时与无效引用均跳过或确定性降级；
- SQLite 开启 WAL、合理同步级别和繁忙超时，降低 PoC 并发读写的瞬时锁竞争；
- 来源同步的交付状态、载荷读取和检疫写入被拆为小型职责单元，异常路径不再重复拼装脱敏元数据；
- 检索权重和回答/升级阈值改成具名常量，注释明确它们必须在工厂 golden set 上重新标定；
- 核心身份、检索、编排、持久化、清单和主数据模块增加“设计原因/安全不变量”注释；
- 新增开发指南、代码架构导览和面试作品集指南；
- `make check` 增加 Python/JavaScript 语法质量门禁；
- 测试夹具显式提交并关闭数据库连接，`ResourceWarning` 严格模式通过。

## 招聘视角的强项

1. **场景选择具体**：围绕良率异常、Failure Code 和 RCA 首轮取证，而不是泛化问答；
2. **端到端所有权**：数据契约、检索、API、UI、工作流、持久化、测试和运维说明都可运行；
3. **安全和治理进入代码**：OIDC、ABAC、版本、引用、签名来源、检疫和人工审批不是 PPT 占位符；
4. **工程判断可辩护**：能说明为什么保留确定性控制层，以及模型、向量库和事件系统分别放在哪个受控边界；
5. **边界诚实**：不使用真实希捷数据，不冒充内部集成，不编造业务收益。

## 仍需现场或企业能力

- 真实 SeaTrack 只读接口、字段字典、服务身份和网络通道；
- 真实企业 IdP、组/entitlement、密钥轮换、吊销和身份生命周期验收；
- 企业批准的文档来源、DLP、恶意内容扫描、留存和撤销传播；
- BM25、多语言 embedding、reranker，以及企业批准的模型端点、证书、密钥和语义引用评测；
- Kafka 或企业调度平台、集中数据库、日志/Trace、指标和告警；
- 工程师标注的 golden set、红队集、影子模式和业务基线。
