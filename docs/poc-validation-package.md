# Seagate 无锡工厂 RAG PoC 现场验证包

- 版本：`0.1`
- 日期：`2026-07-29`
- 建议 PoC：SelfTest 良率异常首轮分诊
- 状态：工厂访谈前假设稿

> 本方案基于 Seagate 公开资料和合成数据 MVP 编制，不包含 Seagate 内部资料，也不代表 Seagate 的真实 Failure Code、产品、工艺参数、组织分工或审批流程。文中所有流程与目标都需要由无锡工厂确认。

## 1. 这次要验证的业务决定

不是先决定“采用哪个大模型”，而是先回答：

> 当 HDD 测试良率或某类失败现象突然异常时，把制造上下文、有效工程文档和已关闭历史案例组合起来，能否让工程师更快形成一份有证据、可执行、可追溯的首轮排查方案？

如果 6 周 PoC 不能在真实历史问题上证明检索有用、引用正确、边界安全和时间节省，就不进入生产化。

## 2. 为什么这个场景靠近无锡业务现场

截至 2026 年 7 月的公开信息给出四个信号：

1. Seagate 最新公开的 ISO 9001 证书把无锡站点范围描述为 Drive、Head Stack Assembly（HSA）和 Systems Manufacturing；
2. 无锡 Product Performance Engineering 岗位直接涉及 HDD 性能、良率监控与分析、来料/装配问题早期检测以及工厂实时部署；
3. 无锡 Global Factory IT 岗位明确提出为 SeaTrack MES 开发 GenAI 知识管理方案；
4. Seagate 公开介绍其制造 AI 已用于异常检测、根因分析、预测性维护、质量与工程效率提升。

这些信息只能证明“业务方向合理”，不能证明无锡现场的实际流程、字段和优先级。PoC 的第一阶段必须让工厂团队确认：SelfTest 是否是正确切口、SeaTrack 能提供哪些上下文、谁对首轮分诊负责。

## 3. 问题假设

### 3.1 触发事件

监控、工程师或班组发现某产品在测试环节出现：

- First Pass Yield 下降；
- 某 Failure Code 或失败模式异常升高；
- 异常集中于单站、多站、同一物料批次或软件版本；
- 当前表现与正常基线明显不同。

### 3.2 当前可能存在的摩擦

以下均为待验证假设：

- 上下文散落在 MES、报表、SOP、FA 报告、变更记录和交接信息中；
- 同一个失败现象可能由设备、物料、程序、固件或产品配置等不同因素造成；
- 搜到“同一个 Failure Code”不等于搜到“同一个问题”；
- 文档版本、适用产品和权限不容易同时判断；
- 调查结论未被结构化沉淀，下一次仍需要从头查找；
- 通用聊天机器人可能给出无引用或越权的确定性建议。

### 3.3 PoC 的工作对象

PoC 只支持首轮分诊，不负责确认最终根因。输入包括：

- 产品/产品族；
- 产线、站点、设备；
- 测试阶段与失败现象；
- 时间窗口与异常范围；
- 物料批次；
- 测试程序与固件版本；
- 工程师的自然语言描述。

输出包括：

1. 相似历史案例及其相似/不相似条件；
2. 当前有效文档的精确引用；
3. 按信息增益和风险排序的首轮检查项；
4. 已知事实、系统推断和待人工确认项的分离；
5. 低置信度升级、越权拒绝和完整审计记录。

## 4. 明确边界

### PoC 可以做

- 读取经批准的只读样本数据；
- 根据结构化制造上下文检索案例；
- 检索有效版本的 SOP、OCAP、Failure Code 定义、FA 报告和变更记录；
- 给出证据化的检查建议；
- 记录工程师反馈和最终处置结果；
- 发现证据不足时停止推断并升级。

### PoC 不可以做

- 自动确认根因；
- 自动修改工艺、测试参数或程序；
- 自动跳过测试、停止/启动设备或产线；
- 自动隔离、报废或放行产品；
- 绕过权限读取受限文档；
- 把合成 Failure Code `F127` 当作 Seagate 真实代码。

## 5. 最小可验证流程

```mermaid
flowchart LR
    A["异常触发"] --> B["自动补齐制造上下文"]
    B --> C["检索相似案例与有效文档"]
    C --> D["生成首轮检查顺序与引用"]
    D --> E["工程师接受、修改或拒绝"]
    E --> F["记录结果并形成可审核案例"]
```

每一步都要能回答“数据来自哪里、谁有权看、证据是否仍有效、谁做了最终决定”。

## 6. 6 周 PoC 计划

| 周次 | 重点 | 主要输出 | 退出条件 |
| --- | --- | --- | --- |
| 第 1 周 | 现场访谈与范围锁定 | 当前流程、角色、字段、场景定义 | 工艺/产品/质量/IT 对主场景达成一致 |
| 第 2 周 | 数据与知识盘点 | 字段映射、文档清单、脱敏方案 | P0 数据和文档样本可用 |
| 第 3 周 | 接入与索引 | 结构化上下文、权限元数据、检索基线 | 样本可重复加载并有数据质量报告 |
| 第 4 周 | 离线评测 | 50–100 个历史问题、专家标准答案、错误分析 | 检索与引用达到拟定门槛 |
| 第 5 周 | 影子试运行 | 工程师并行使用、不影响现有流程 | 安全边界通过，收集真实反馈 |
| 第 6 周 | 复盘与决策 | KPI、风险、技术差距、生产化建议 | Go / Adjust / Stop 决策 |

## 7. 建议验收门槛

门槛是 PoC 前建议值，必须由工厂负责人确认，不是现有系统成绩。

| 维度 | 指标 | 建议门槛 | 说明 |
| --- | --- | --- | --- |
| 检索 | Top-3 有用案例命中率 | `>= 70%` | 专家认为前三条至少一条对首轮分诊有帮助 |
| 证据 | 引用正确率 | `>= 95%` | 引用内容支持对应结论，版本与适用范围正确 |
| 安全 | 高风险越权拒绝率 | `100%` | 修改参数、跳测、放行等请求必须拒绝 |
| 效率 | 首轮分诊中位时间下降 | `>= 30%` | 与同类历史流程基线对比 |
| 采用 | 工程师愿意继续使用 | `>= 70%` | 影子试用问卷和任务完成记录 |

任何一个安全红线失败，都不以平均分抵消。

## 8. 组织与角色

| 角色 | 建议职责 | PoC 最小投入 |
| --- | --- | --- |
| 业务负责人 | 定义价值、范围和 Go/Stop 决策 | 每周评审 30 分钟 |
| 产品/性能工程 SME | 定义异常上下文、评审案例相关性 | 2 人，每周 2–3 小时 |
| 工艺/设备工程 SME | 验证设备与过程检查项 | 1–2 人，按案例参加 |
| 质量/FA | 确认证据、结论与发布规则 | 1 人，每周 1–2 小时 |
| GFIT / MES | 提供只读字段、接口和运行环境 | 1–2 人 |
| 信息安全/数据治理 | 审核密级、权限、留存与模型边界 | 里程碑评审 |

## 9. 启动前需要批准的事项

1. 指定 1 名业务负责人和 2 名工程 SME；
2. 确认 PoC 是否聚焦 SelfTest，或替换为更高频的测试/良率异常环节；
3. 批准一套脱敏、只读、离线样本；
4. 选取 50–100 个已关闭历史问题作为盲测集；
5. 确定工厂允许的部署边界：内网、私有云或其他批准环境；
6. 确定哪些文档不可进入索引以及谁能访问；
7. 确认验收指标与 Go / Adjust / Stop 决策人。
