# Seagate Wuxi SelfTest Yield Anomaly Copilot

## 业务需求文档（v0.1）

- 文档状态：讨论稿
- 当前阶段：业务需求定义
- 项目类型：制造现场知识检索与异常排查辅助系统
- 目标场景：HDD SelfTest 测试良率异常
- 目标地点：Seagate 无锡工厂（概念方案，尚未获得工厂内部资料）

## 1. 项目背景

Seagate 无锡基地从事硬盘及相关组件、系统的制造和测试。公开岗位信息显示，其产品工程、工艺、质量和失效分析团队需要持续改善产品良率、测试时间和质量，并对制造与测试异常进行根因分析。

本项目暂定聚焦于以下现场问题：

> 当某产品型号在 SelfTest 测试环节出现失败率或特定 Failure Code 异常升高时，工程师需要在多个系统和文档中查找历史案例、操作规范、变更记录与分析报告，难以及时形成有证据的首轮排查方案。

当前没有 Seagate 内部数据、系统接口说明或现场访谈资料。因此，文档中涉及具体流程、字段和角色分工的内容均为待验证假设，不代表工厂实际流程。

## 2. 要解决的核心痛点

### 2.1 痛点描述

测试良率异常发生后，相关信息可能分散在 MES、测试日志、历史异常报告、失效分析报告、SOP、Jira、变更记录及人员经验中。工程师需要手动查找、比对和询问，造成：

- 历史相似案例难以快速发现；
- 相同或相似问题被重复排查；
- 新人与非本领域工程师过度依赖资深人员；
- 首轮排查缺少统一、可追溯的证据；
- 跨产品、工艺、质量和失效分析团队的信息交接效率低；
- 问题关闭后的经验未被标准化沉淀，后续难以复用。

### 2.2 项目目标

系统应帮助现场工程师：

1. 根据产品、产线、测试站、失败代码和异常现象找到历史相似案例；
2. 汇总与本次异常相关的 SOP、历史根因、处置措施和变更信息；
3. 生成有证据、有顺序、可供工程师验证的首轮排查建议；
4. 明确标注事实、历史经验、系统推断和未知信息；
5. 在异常关闭后，将处理过程沉淀为可复用的标准案例。

### 2.3 项目不承担的职责

MVP 不应：

- 自动认定最终根因；
- 自动修改设备参数、工艺参数或测试程序；
- 自动停止或启动产线；
- 自动放行、报废或隔离产品；
- 替代质量、产品、工艺或失效分析工程师的签核；
- 覆盖全厂所有业务知识；
- 直接训练预测性维护或视觉缺陷检测模型；
- 在无证据的情况下生成确定性结论。

## 4. MVP 使用场景

### 4.1 场景名称

SelfTest 测试失败率异常的首轮排查。

### 4.2 场景触发条件

满足以下任一条件时，由工程师主动发起查询：

- 某 Failure Code 的发生率明显高于正常水平；
- 某测试站、产线或产品族的 First Pass Yield 降低；
- 新物料、新固件或新测试程序导入后出现异常；
- 不同站点或批次出现相似测试失败；
- 现场人员需要判断是否存在历史相似案例。

具体报警阈值不由 MVP 决定，暂由现有 MES、监控系统或工程师提供。

### 4.3 示例输入

> 产品型号 X 在 Line 2、SelfTest Station 04 从 14:20 开始出现 Failure Code F127 增加。当前批次使用 HSA Lot H2407，测试程序版本为 V3.8。历史上有没有类似问题？建议先检查什么？

### 4.4 期望输出

系统应按照固定结构返回：

1. **异常摘要**：复述已知的产品、产线、站点、时间、失败代码和批次信息；
2. **相似案例**：列出最相关的历史案例及相似点、不同点；
3. **建议排查顺序**：按优先级给出可验证的检查步骤；
4. **可能关联因素**：列出设备、物料、工艺、固件或测试程序等候选方向；
5. **缺失信息**：指出继续判断所需但当前没有的数据；
6. **升级条件**：说明何时应转交产品、质量、工艺或失效分析团队；
7. **证据引用**：为关键结论提供文档名称、案例编号、版本、日期和可访问链接；
8. **置信说明**：标明回答是直接证据、历史类比还是系统推断。

## 5. 目标业务流程

### 5.1 异常提交

用户输入或选择：

- 产品型号或产品族；
- 产线；
- 测试站或设备编号；
- Failure Code；
- 异常开始时间；
- 当前失败率或良率变化；
- 物料批次；
- 固件版本；
- 测试程序版本；
- 自由文本现象描述；
- 可选的测试日志或截图。

并非所有字段都必须填写。系统应明确提示缺失的关键上下文。

### 5.2 信息检索

系统根据用户权限，检索：

- 历史良率异常案例；
- 失效分析报告；
- 8D 或纠正措施报告；
- SelfTest Failure Code 说明；
- 有效版本的 SOP 和检查清单；
- 固件、测试程序、物料和工艺变更记录；
- 设备维修、校准及异常记录；
- 班次交接或工程问题记录。

### 5.3 结果分析与展示

系统对检索结果进行相关性排序，说明案例为何相似，并生成首轮排查建议。所有关键结论必须能够回到原始证据。

### 5.4 人工确认

工程师可以：

- 采纳或拒绝某项建议；
- 标记相似案例是否真正相关；
- 补充实际检查结果；
- 对回答进行“有用、部分有用、无用、存在风险”反馈；
- 将问题升级给指定团队。

### 5.5 异常关闭与知识沉淀

问题关闭后，系统协助生成标准案例草稿，至少包含：

- 异常现象；
- 影响范围；
- 产品、设备、物料和版本上下文；
- 排查步骤及结果；
- 已排除原因；
- 临时处置措施；
- 最终确认根因；
- 永久纠正措施；
- 验证结果；
- 适用和不适用条件；
- 审核人与审核日期。

案例必须由有权限的工程师审核后才能进入正式知识库。

## 8. 回答质量与安全要求

### 8.1 证据要求

- 关键事实必须引用来源；
- 引用必须定位到具体案例或文档内容；
- 系统不得把搜索结果标题当成完整证据；
- 已失效文档可以作为历史背景，但必须明确标识；
- 多个来源冲突时应展示冲突，不得自行选择一个作为事实；
- 未检索到可靠证据时，应明确回答“当前资料不足”。

### 8.2 内容分级

回答应区分：

- **已知事实**：来自本次异常输入、MES 或有效文档；
- **历史经验**：来自已审核的相似案例；
- **系统推断**：根据相似性形成的候选方向；
- **未知信息**：当前缺失且可能影响判断的数据。

### 8.3 高风险操作控制

涉及以下内容时，系统只能引用获批准的流程，不得自行编造操作：

- 产品隔离或放行；
- 设备停机或恢复；
- 参数调整；
- 跳过测试；
- 固件或测试程序变更；
- 报废处置；
- 安全联锁相关操作。

## 9. 非功能需求

| 类别 | 初步要求 |
| --- | --- |
| 响应速度 | 普通知识查询目标在 10 秒内返回；复杂日志分析可异步处理 |
| 可用性 | 适配工厂桌面端，后续再评估平板或移动端 |
| 可追溯性 | 每次回答均可还原检索来源和使用的知识版本 |
| 权限 | 权限控制必须发生在检索阶段，而不是回答生成后 |
| 数据安全 | 内部制造数据不得发送到未经批准的外部模型服务 |
| 稳定性 | 知识库或模型暂时不可用时，不得输出无来源的替代答案 |
| 可维护性 | 支持文档版本更新、失效和重新索引 |
| 可评估性 | 保存评测问题、期望证据、回答和人工评分 |

以上指标需要在了解 Seagate 的网络、终端和安全要求后重新确认。

## 10. MVP 验收标准

在使用合成数据的概念验证阶段，MVP 至少应满足：

1. 准备不少于 30 个结构化历史异常案例；
2. 准备不少于 10 份 SOP、Failure Code 或变更说明类文档；
3. 建立不少于 20 个评测问题，覆盖正常、模糊、冲突、无答案和越权场景；
4. 对有答案问题，关键结论均能返回正确证据；
5. 对无答案问题，系统不编造根因或不存在的文档；
6. 对过期 SOP，系统能够明确提示版本状态；
7. 对冲突资料，系统能够展示冲突并要求人工确认；
8. 对缺少产品、站点或 Failure Code 的问题，系统能够提示补充必要信息；
9. 至少支持一次完整演示：异常提交、案例检索、排查建议、用户反馈、案例沉淀；
10. 所有数据和界面明确标识为虚构演示，不冒充工厂真实数据。

## 11. 业务成功指标

真实试点阶段建议采集基线后再设目标值，核心指标包括：

- 从异常发现到形成首轮排查方案的中位时间；
- 历史相似案例被成功复用的比例；
- 工程师认为结果“有用或部分有用”的比例；
- 回答关键结论的引用准确率；
- 无依据确定性结论的发生率；
- 重复排查步骤数量；
- 新工程师独立完成初步排查所需时间；
- 异常关闭后形成标准知识案例的比例。

不建议在没有现场基线的情况下，提前承诺固定的良率提升或停机时间下降幅度。

## 13. 当前需求结论

MVP 的唯一核心任务为：

> 在 SelfTest 测试良率异常发生后，基于历史异常案例和有效工程文档，为现场工程师快速生成有证据、可验证的首轮排查方案。

任何不能直接支持这一任务的功能，默认不进入首期范围。
